OntoGraph research · gUFO usage examples · updated 27 November 2026

One engine for OntoUML:
load models, feed data, and query.

OntoGraph productises OntoUML into a single engine: you load many models, as cartridges, feed them instance data, and query the result. The nine gUFO usage examples are the acceptance suite for that semantic core — proof that the engine stays faithful to UFO, OntoUML and gUFO. ontograph-dsl-tonto is the side-channel that takes Tonto, NEMO's text DSL for OntoUML, and lowers it into the same engine without changing a model to satisfy Tonto.

Product direction

The aim is a utility that drives grounded context for AI and can act as a second brain: many OntoUML models and their data, queried as a stable semantic core. This edition does not ship an AI assistant or a prompt layer. What the engine already does today is load OntoUML (from authored JSON or from Tonto), apply UFO rules, project gUFO, merge instance data, store the result, and answer checks and queries against it.

This page is written so the acceptance evidence can be read in one pass. It takes three things in order:

  1. How each of the nine examples played out. Seven valid models project with no UFO-rule findings and conform to gufoshapes in both pySHACL and Apache Jena 6.2.0. The two invalid variants are caught by OntoGraph's rules and by gufoshapes. Pellet finds all nine consistent, including the invalid ones.
  2. What we found. Every difference from the upstream Turtle is classified. Three genuine modelling differences are pending NEMO review. Tonto 0.9.4 was a cross-check, not an authority: we record where it diverges from published OntoUML/UFO, and where it is right — including an objection we withdrew.
  3. How we executed it. The architecture, a walkthrough of a model Tonto gives us into OntoGraph and a query on the projected graph, and the recorded checks. The numbered evidence — tables, diffs, the portable re-check, the retained run — follows underneath, unchanged in substance.

01 / The nine examples

How each example played out

Each case started from the example prose, as an OntoUML model we authored, plus an OntoGraph instance file. The upstream Turtle at gUFO commit f412254 was a comparison target only. The numbers are from the retained run of 27 November 2026, 07:05:47 Australia/Sydney; the table immediately below is the recorded evidence.

1. Endurant types — valid. No UFO-rule findings. gufoshapes conforms in pySHACL and Jena 6.2.0; Pellet is consistent. Tonto 0.9.4 accepts this model. Used below as the worked walkthrough of a Tonto input into OntoGraph.

2. Objects and their parts — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. Tonto cannot accept an optional same-type sub-collection (a fleet within a fleet). OntoGraph kept the model and recorded a dual verdict: Tonto error, OntoGraph accepted.

3. Qualities and quality values — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. Tonto accepts the model. (When the Rust writer emits Tonto, unspecified cardinalities become [0..*], which is an expressivity gap, not a Tonto error in the literature sense.)

4. Relators and extrinsic aspects — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. Tonto accepts the model. The authoring record notes that the Turtle was read; it was still not used as the projector input.

5. Events — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. Tonto rejects «event» specialising «event» (SemiFinal and Final under Match). OntoGraph kept the specialisation and recorded a dual verdict. Two genuine differences from the upstream Turtle — a MatchParticipation class, and gufo:participatedIn instead of :participatedInMatch with range :Match — are pending NEMO review, as questions, not as corrections of the example.

6. Situations — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. One reviewed difference is not a disagreement: the prose names the sepsis alert but does not state the time it fired, so a begin timestamp that appears only in the Turtle was omitted. The Turtle was read during authoring; it was not the projector input.

7. Higher-order types — valid. No UFO-rule findings; both SHACL engines conform; Pellet is consistent. Tonto accepts the valid model.

1, invalid variant — caught. OntoGraph reports two UFO-rule errors (a «kind» Manager specialising a «role» Employee, which also places a rigid type under an anti-rigid one). gufoshapes reports the same two violations in both engines. Pellet remains consistent, as with the upstream file. Tonto also rejects this model; that is not a Tonto issue, because the model is invalid on purpose.

7, invalid variant — caught. OntoGraph reports one UFO-rule error: Tiger is in the AnimalSpecies partition without being declared disjoint from the other members. gufoshapes reports six violations (Tiger against Lion, Hyena and Elephant, in both directions) because our invalid case extends the full valid model, which already includes Elephant; the upstream invalid file is a minimal excerpt without Elephant. Tonto is right to reject the overlapping generalisation set with an «instantiation» upper bound of 1; it can still miss the partition pitfall when it only sees a categorizer and not @instantiation. How we encoded the pitfall in OntoUML is a question for NEMO.

02 / Findings

What we found

The full classified diffs, reviewed notes and Tonto discussion remain in the evidence sections below. This is the short account.

Every unmatched triple against the upstream Turtle is classified (0 unclassified on all nine cases). Most differences are annotations and ontology headers, individuals that appear only in the Turtle, extra axioms OntoGraph derives from UFO, equivalent OWL forms, or stereotypes OntoUML requires and upstream sometimes leaves untyped. The genuine content differences, recorded in reviewed-differences.v1.json, have had a self-review only. We would value a view on three of them:

  1. Invalid 07, encoding of the pitfall. OntoUML has no way to add a member to a generalization set while omitting only the OWL disjointness, so the pitfall is modelled as a second, non-disjoint set {Tiger} with the same categorizer, which projects as gufo:categorizes alongside gufo:partitions. Is that faithful?
  2. Example 05, MatchParticipation. OntoUML has no instance level, so the reified participation in the prose is an «event» class, of which JordanLeeParticipationInFinal is an instance. Is that an acceptable encoding?
  3. Example 05, range of :participatedInMatch. Upstream, that property has range :Match and is used to link a player to a participation. Under OWL the participation would also be a Match. OntoGraph projects gufo:participatedIn instead. Was the upstream range intended?

Tonto 0.9.4 was a cross-check, not a modelling authority, and no model was changed to satisfy it. ontograph-dsl-tonto lowers and writes Tonto with dual verdicts. It diverges from published OntoUML/UFO in rejecting «event» specialising «event» (example 05) and in being unable to accept an optional same-type sub-collection (example 02). It reads a partition only from @instantiation and (instanceOf …), so it can miss the invalid-07 pitfall when only a generalisation-set categorizer is written. The 0.9.4 CLI has no OntoUML JSON export, and tonto ast can exit 0 on a file that does not parse.

Where Tonto is right, we say so. Its rejection of invalid 07 under genset-contradicts-instantiation matches UML 2.5.1 and Carvalho, Almeida and Guizzardi (CAiSE 2016). We had earlier read isDisjoint as merely leaving disjointness unasserted, and we have withdrawn that objection. Tonto is also right to require a single participant on a «participational» portion, in line with UFO-B. The gap that remains on our side is that OntoGraph's UFO rules do not yet check the Table 3 combination from the 2016 paper.

03 / How we executed it

Engine, cartridges, and a model Tonto gives us

OntoGraph is the engine. A cartridge, in this setting, is a model you load into it — an OntoUML project, with optional instance data — so several can sit in one workspace and be queried together. ontograph-dsl-tonto is not a second engine: it is the library that turns a .tonto file into that same OntoUML project, then hands it to OntoGraph unchanged.

Architecture of the acceptance path

Two ways in — authored OntoUML JSON from the example prose, or a Tonto file lowered by ontograph-dsl-tonto — meet as an OntoUML model. OntoGraph imports and normalises it, evaluates UFO rules, projects gUFO (merging the instance file), and stores the result so it can be queried. The projected Turtle is then checked with pySHACL, Jena, Pellet, a classified comparison with the upstream Turtle, and the frozen oracles.

A worked path: example 01, from Tonto into a query

Example 01 is a case Tonto 0.9.4 accepts. The Tonto below is the published fixture for that example (an excerpt of the types and generalisation sets). Instance data is supplied separately, because OntoUML has no instance level.

ontology gufo-examples-01-endurant-types

category Agent of functional-complexes
kind Person specializes Agent
kind Organization specializes Agent
subkind University specializes Organization
phase Child specializes Person
phase Adult specializes Person
role Student specializes Person
role Employee specializes Person
roleMixin Customer of functional-complexes specializes Agent
phaseMixin ActiveAgent of functional-complexes specializes Agent
phaseMixin InactiveAgent of functional-complexes specializes Agent

disjoint genset AgentKinds {
    general Agent
    specifics Person, Organization
}

The installed CLI lowers that file to an OntoUML project, then projects it to gUFO. These are the real command names and flags:

ontograph --json tonto-import 01-endurant-types.tonto --output model.json

ontograph --json tonto-gufo-project request.json

tonto-import also accepts --project-id, --namespace and --created. tonto-gufo-project takes one request file, with the Tonto text as modelSource, the instance file as instanceSource, and the same projector options used for the acceptance suite:

{
  "modelSource": "…contents of 01-endurant-types.tonto…",
  "instanceSource": "…contents of instances.json…",
  "options": {
    "profileRef": "ontograph.gufo.ontouml-examples.v1",
    "iriPolicy": "name",
    "enforceRules": true
  },
  "lowering": { "projectId": "…optional; pins the OntoUML project id…" }
}

The same projector is also available as ontograph --json ontouml-gufo-project request.json when the model is already OntoUML JSON. A test of the installed CLI locks that the two paths produce identical Turtle and the same graph digest for example 01. A Tonto round-trip of all nine examples, run with the same binary as the retained acceptance run, likewise produced identical gUFO on every case.

05 / Differences

Differences from the upstream Turtle

Because the models were authored from the example prose, the projected gUFO is not identical to the published Turtle. Every unmatched triple in the retained run was classified. The ordinary categories are annotations and ontology headers, individuals that appear only in the Turtle and not in the prose, extra axioms that OntoGraph derives from UFO, equivalent OWL forms, and stereotypes that OntoUML requires and upstream sometimes leaves untyped. The genuine content differences are recorded in reviewed-differences.v1.json. They have had a self-review only. NEMO review is still pending, and the following are offered as questions, not as corrections of the upstream examples.

  1. Invalid 07, encoding of the pitfall. OntoUML has no way to add a member to a generalization set while omitting only the OWL disjointness, so the pitfall is modelled as a second, non-disjoint generalization set {Tiger} with the same categorizer. That set projects as gufo:categorizes in addition to the existing gufo:partitions. Is that a faithful encoding of the invalid-07 pitfall?
  2. Example 05, MatchParticipation. OntoUML has no instance level and cannot type an individual by a gUFO class directly, so the reified participation in the prose is modelled as an «event» class MatchParticipation, of which JordanLeeParticipationInFinal is an instance. Pellet then derives the upstream typing as a gufo:Participation. Is that an acceptable OntoUML encoding?
  3. Example 05, range of :participatedInMatch. In the upstream Turtle, :participatedInMatch has range :Match and is used to link :JordanLee to :JordanLeeParticipationInFinal. Under OWL that would also classify the participation as a Match. OntoGraph instead projects gufo:participatedIn from Player to MatchParticipation. Was the upstream range intended?

A further reviewed difference in example 06 is not a modelling disagreement: the prose names the sepsis alert but does not state the time it fired, so the begin timestamp that appears only in the upstream Turtle was omitted.

No class or instance diagrams are published in this edition. The OntoUML models are in JSON, with the projected Turtle beside them.

07 / Tonto 0.9.4

A cross-check, not a modelling authority

Tonto 0.9.4, NEMO's text DSL for OntoUML, was used as a cross-check. It is not the authority for these models, and no model was changed to satisfy it. OntoGraph provides an OntoUML-faithful Tonto conversion, ontograph-dsl-tonto, with dual verdicts: Tonto's own check, and OntoGraph's correction where Tonto diverges from published OntoUML/UFO. A Tonto round-trip of the nine projected graphs, run with the same binary as the retained acceptance run, produced identical gUFO on all nine cases. That test needs the private runtime and is not in the portable bundle.

Places where Tonto 0.9.4 diverges from published OntoUML/UFO, or where its tooling is incomplete, include:

  • «event» specialising «event». Tonto rejects this, so it rejects example 05 (SemiFinal and Final under Match). Published OntoUML allows an «event» class to specialise an «event» class, and that is how the upstream example is written.
  • An optional same-type sub-collection. Tonto's sub-collection-multiplicity and parthood-descends-forever rules cannot both be satisfied for a collective with an optional sub-collection of its own type, so a fleet-within-a-fleet as in example 02 cannot pass tonto check.
  • A partition is not read from a generalization set's categorizer. Tonto detects a partition only from @instantiation and (instanceOf …), so it can miss the invalid-07 pitfall when the categorizer is written only as a generalization-set categorizer.
  • No OntoUML JSON export in the 0.9.4 CLI, and tonto ast exits 0 on some inputs that do not parse, printing a recovered empty tree.

Where Tonto is right, we say so. Its rejection of invalid 07 under genset-contradicts-instantiation matches UML 2.5.1 and Carvalho, Almeida and Guizzardi (CAiSE 2016): a generalization set that is not disjoint is an overlapping one, and combining that with an «instantiation» upper bound of 1 is invalid. We had earlier read isDisjoint as merely leaving disjointness unasserted, and we have withdrawn that objection. Tonto is also right to require a single participant on a «participational» portion, in line with UFO-B: gufo:Participation has exactly one participant.

The gap that remains on our side is that OntoGraph's own UFO rules do not yet check that Table 3 combination from the 2016 paper. That is an OntoGraph rule to add, not a Tonto issue.

11 / Limits

What this edition does not claim

  • The OntoGraph engine is private. The portable bundle checks published outputs against gufoshapes; it does not rerun the projection.
  • There is no independent human ontologist review yet. Self-review of the classified differences is not a substitute for one.
  • No claim is made of parity with the official OntoUML validator, the OntoUML server, or the Visual Paradigm plugin's "Export to gUFO".
  • The two invalid cases are the pitfalls that ship with the upstream examples. Relators, qualities, events and situations still have no negative acceptance case in this suite. The ordering extension of example 05 is ours, and is labelled as such.
12 / Questions

Where a review would help most

  1. The invalid-07 encoding, the MatchParticipation class, and the range of :participatedInMatch. These are the three pending questions under differences.
  2. Time-qualified grounding. When a role holds only while a relator exists, should a gUFO projection express that through the relator's own begin and end points, through situations, or through something else?
  3. Identity and dependence in partial snapshots. If a graph is a partial snapshot, for example an appointment whose organisation simply isn't recorded, should a UFO-grounded system report a violation (closed world) or an unknown participant (open world)?

Related work

This work builds on UFO (Guizzardi, Ontological Foundations for Structural Conceptual Models, 2005; Guizzardi et al., UFO: Unified Foundational Ontology, Applied Ontology, 2022) and on OntoUML as the language for UFO-compliant models. The target is gUFO (Almeida, Guizzardi, Sales and Fonseca, gUFO: A Gentle Foundational Ontology for Semantic Web Knowledge Graphs, 2026), validated with gufoshapes. The closest existing tool is the OntoUML-to-gUFO transformation in the OntoUML server, which the Visual Paradigm plugin uses for "Export to gUFO". OntoGraph doesn't replace it. Carvalho, Almeida and Guizzardi, CAiSE 2016, is the published basis for treating a non-disjoint generalization set as overlapping, which is why we withdrew our earlier objection to Tonto on that point.

13 / OntoGraph's own worked case

Research appointments: modelling under revision

Separately from the gUFO usage examples, we built a small case of our own about people, organisations and research appointments, to test how OntoGraph keeps identities connected across views. Its evidence is recorded, but the model has known problems, and we'll revise it before asking for feedback on it.

Known issues
  • The «role» Researcher isn't connected to any mediation. Appointment mediates Person and Organization directly, whereas gUFO's relators example mediates the roles Employee and Employer.
  • Time uses a custom comp:begin/comp:end pair instead of gUFO's own properties, such as gufo:hasBeginPointInXSDDateTimeStamp.
  • The appointment data is contrived: intervals of two to three hours, a leap day and a +14:00 offset, chosen to test edge cases rather than to look realistic.
  • The Mass quality and the Seminar event are in the model without any explanation of why they are there.
  • The generated graph types Appointment and Mass as gufo:EndurantType, as subclasses of gufo:Relator and gufo:Quality. That choice hasn't been justified.
